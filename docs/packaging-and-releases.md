# Packaging, signing, and auto-update

Section 27 of `docs/ARCHITECTURE.md` recommends "the Electron ecosystem's standard builder +
updater tooling, with code signing/notarization on every platform." This document explains what's
actually wired up in this repository, what still needs credentials only you can provide, and how
to produce a real release build.

## What's real right now

- `electron-builder.yml` — a real, working packaging config (appId, product name, mac/win/linux
  targets, `asarUnpack` for the native modules this app depends on).
- `electron-updater` is wired into `electron/main.js`: on a packaged app's startup,
  `autoUpdater.checkForUpdatesAndNotify()` runs against this repository's GitHub Releases (per
  `electron-builder.yml`'s `publish` config). It's guarded by `app.isPackaged`, since a
  from-source dev run has no installed artifact to update and no `app-update.yml` file (that's
  generated by `electron-builder` at package time).
- `npm run package:dir` — builds an **unsigned**, unpacked app for the current platform, useful
  for quickly checking the packaging config still works. Verified for real against this exact
  project: it correctly produces `release/linux-unpacked/`, correctly excludes
  `better-sqlite3-multiple-ciphers`'s and `@napi-rs/keyring`'s native `.node` binaries from the
  asar archive (confirmed via `npx asar list` — native addons can't be `dlopen`'d from inside an
  asar), and correctly generates `app-update.yml` for `electron-updater` to read.
- `npm run package` — the same, but produces the final installer artifacts (`.dmg`/`.zip` on
  mac, `.exe` via NSIS on Windows, `.AppImage`/`.deb` on Linux) instead of just an unpacked
  directory. Still unsigned without the credentials below.

**Important housekeeping**: both scripts run `electron-rebuild`, which recompiles
`better-sqlite3-multiple-ciphers`'s native binary against *Electron's* Node ABI. That leaves the
binary in the wrong ABI for running `npm test`/`vitest` afterward (which run under your system
Node). Run `npm run rebuild:native:node` to switch it back before testing again — this is a
pre-existing quirk of this project's native-module workflow (see `electron:dev` in
`package.json`), not something new introduced by packaging.

## What's NOT real yet — and can't be, without your own credentials

Nothing in this repository can generate real code-signing certificates or notarization
credentials — those come from Apple and from a commercial code-signing certificate authority, and
require identity verification and (for Apple) a paid developer account. Without them:

- **macOS**: `npm run package`/`release` produces an **unsigned** app. macOS Gatekeeper will warn
  users it's from an "unidentified developer" and may refuse to open it entirely on first launch.
- **Windows**: produces an **unsigned** installer. Windows SmartScreen will show a warning on
  first run ("Windows protected your PC").
- **Linux**: no equivalent OS-level gate exists, so an unsigned `.AppImage`/`.deb` from this
  config is already a complete, distributable artifact — nothing missing here.

### Supplying real signing credentials

`electron-builder` reads these standard environment variables automatically — set them (e.g. as
CI secrets) and `npm run release` produces genuinely signed, notarized, auto-updatable builds with
no config changes needed:

| Variable | Platform | What it is |
|---|---|---|
| `CSC_LINK` | mac + win | Path or URL to your `.p12` code-signing certificate |
| `CSC_KEY_PASSWORD` | mac + win | That certificate's password |
| `APPLE_ID` | mac (notarization) | Your Apple Developer account email |
| `APPLE_APP_SPECIFIC_PASSWORD` | mac (notarization) | An app-specific password for that account |
| `APPLE_TEAM_ID` | mac (notarization) | Your Apple Developer Team ID |
| `GH_TOKEN` | publishing | A GitHub token with `repo` scope, so `electron-builder` can upload the built artifacts to this repo's Releases (the `publish` provider in `electron-builder.yml`) |

Where to get each of these is outside this repository's control — an Apple Developer Program
enrollment ($99/year) for the Apple credentials, a certificate authority (e.g. DigiCert, Sectigo)
for the Windows certificate, and a GitHub personal access token or fine-grained token for
`GH_TOKEN`.

### Auto-update, once signed

Once a signed build is published to this repo's GitHub Releases (`npm run release` with the above
env vars set), every subsequent packaged install of Outboundly will check for and offer that new
version automatically via `electron-updater`, per Section 27's "trustworthy, signed auto-updates"
requirement. `electron-updater` itself refuses to apply an update whose signature doesn't match
the currently-installed app's, so an unsigned build and a signed build can never be silently
substituted for one another.

## Scripts reference

| Script | What it does |
|---|---|
| `npm run electron:dev` | Runs the app from source, unpacked, for development |
| `npm run package:dir` | Unsigned, unpacked package for the current platform (fast, for checking the config) |
| `npm run package` | Unsigned, full installer artifacts for the current platform |
| `npm run release` | Signed (if credentials are set) installer artifacts, published to this repo's GitHub Releases |
